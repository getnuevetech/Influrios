Transitions (finding 4) · product semantics

  1. Marketplace invitations follow APPLICATION_TRANSITIONS: “I'm interested” → RESPONDED, Ask a question → NEGOTIATING, Decline → DECLINED. None of these accepts work or drafts a contract. Only the business moves it to ACCEPTED.
  2. Asking a question does not complete the invitation. It stays open, with the business to act next. Decline is still available.
  3. Whose turn it is (turn = invitee / business / none) is persisted and changes only on actions. A business answer changes the turn only as the §2.2b matrix says: before interest is recorded it returns the turn to you (“Northwind Studio replied”: I'm interested · Ask another question · Decline); after interest, a follow-up answer keeps the business's turn and arrives as a message only.
  4. Reading never changes turn. Opening the invitation, the reply notice or the Messages thread marks them read, but the banner, attention row, badge and task stay until you respond.
  5. Defect P1-D1 (code): today there's no NEGOTIATING → RESPONDED transition, so interest can't be recorded after a question. The design is the target; the code must add that transition. The limitation is not adopted as UX.
  6. Actions follow one matrix (master-spec §2.2b) on status + turn + interest recorded + open question; the server enforces the same matrix. Follow-up questions after Interested are an explicit exception: turn stays with the business and nothing is added to your counts.
  7. Team invitations only offer Accept / Decline (team-proposal member status). No Interested or question.
  8. Badge, banner and attention clear only when turn leaves the invitee (a persisted response, or withdrawn / expired).

Failure, retry, concurrency

  1. One idempotency key per logical submission, bound to the signed-in actor + invitation + payload. Retries of an unresolved submission reuse it; after an outcome, the next submission gets a new key even with identical text. The same key with a different binding is refused.
  2. Timeout: show “We couldn't confirm your response” and look up the idempotency record, not the invitation status (which can look unchanged while the write is still processing). Outcomes: saved → success · rejected → reason · processing → Check again · no record / lookup failed → Try again with the same key.
  3. The draft is kept and locked while its submission is unresolved, including after Close. It can be edited only after the outcome is saved or rejected.
  4. Buttons disable while sending, to prevent a double submit.
  5. Concurrent withdrawal or expiry: the server rejects the reply (“no longer open”). The popup swaps to the withdrawn message, and the list, badge and attention refresh from the server. No optimistic decrement before success.
